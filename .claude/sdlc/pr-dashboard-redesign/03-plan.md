# Frontend redesign: PR dashboard — implementation plan

## Current state (grounding facts, from reading the code)
- `components/PrList.tsx` is 583 lines, one file, `'use client'` at the top
  — the entire tree (filter tabs, every card, every action panel) is one
  client component. It owns `prs` state + the Supabase Realtime
  subscription, so the outer shell legitimately has to be client-side.
- `app/layout.tsx` still has the default `create-next-app` metadata
  (`title: "Create Next App"`) — a real, currently-failing Lighthouse
  SEO/Best-Practices item, unrelated to the redesign but cheap to fix while
  in this area.
- `app/globals.css` sets `body { font-family: Arial, Helvetica, sans-serif }`
  — this **overrides** the Geist fonts that are loaded via `next/font` and
  wired into `@theme inline` as `--font-sans`/`--font-mono`. The custom font
  has never actually been rendering. Also worth fixing while in this file.
- No shadcn/ui in the repo yet: no `components.json`, no Radix/`cva`/
  `clsx`/`tailwind-merge` deps.

## Architecture decisions

**shadcn/ui `init` will rewrite `globals.css` and can break the Geist
fonts** — this is a documented gotcha (Tailwind v4's `@theme inline`
resolves CSS vars at parse time, so `--font-sans: var(--font-geist-sans)`
silently resolves to nothing, a circular/broken reference). Plan explicitly
includes the fix (literal font family names in `@theme inline`, font
variable classNames moved from `<body>` to `<html>`) as its own checked
step, not left to be discovered later.

**shadcn's default `Avatar`/`AvatarImage` renders a plain `<img>`, not
`next/image`** — since Performance is an explicit target and the existing
avatars already use `next/image` correctly (sized, remote-pattern
configured), we keep that: `Avatar`'s shell/styling gets used, but
`AvatarImage`'s internals get customized to wrap `next/image` (this is the
actual point of shadcn — you own the copied-in source) rather than
reverting to an unoptimized `<img>`.

**Split `components/PrList.tsx` into `components/pr-list/*`** (alternative
considered: restyle in place, single file). Rejected the single-file option
— 583 lines is already hard to navigate, and this pass touches literally
every part of it, so it's the natural moment to split before it grows
further. This is a pure reorganization step (zero visual/behavioral change),
done first and verified before any restyling, so if something breaks
afterward it's obviously not the file move.

**Merge confirmation moves from inline-expand to a shadcn `AlertDialog`**
— the one genuine interaction-shape change in this pass (everything else is
styling/markup only). Reasoning: shadcn's own guidance is explicit —
`AlertDialog`, not `Dialog`, for destructive confirmation, and merging is
irreversible. This doesn't touch the non-goal locked in `/grill-requirements`
(which was about the top-level action *toolbar* staying visible/not
becoming an overflow menu) — it's scoped to how one action's own confirm
step renders. `AlertDialog` is not a blocking native `confirm()`, so it
doesn't reintroduce the original reason that was avoided (blocking
automated browser testing).

**Server/Client Component boundary stays as-is for now** — not restructured
in this pass, even though the whole list being one client component is a
plausible Performance lever (e.g. passing server-rendered card shells as
`children` into client action-panel wrappers). Deliberately deferred:
`/optimize` runs against real Lighthouse numbers first; this only gets
picked up if the actual audit shows it's needed, per the pipeline's own
"fix what's flagged, not what plausibly should be" philosophy. Speculative
restructuring here would also risk the "presentation-layer only" boundary
this feature is scoped to.

**Dark mode stays OS-preference-only** (already decided in
`02-grilled-requirements.md`) — note this is a deliberate deviation from
`vercel:shadcn`'s general default recommendation (dark-mode-first for
dashboards); overridden because it was an explicit, already-resolved product
call, not revisited here.

## shadcn/ui components used, and why
`button`, `card`, `badge`, `avatar`, `tabs`, `textarea`, `select`, `alert`,
`alert-dialog`, `skeleton`, `separator` — plus `lucide-react` for icons.
Nothing beyond this set (no `dialog`, `dropdown-menu`, `command`, etc.) —
matches the grilled requirement that the action toolbar stays flat, not a
menu.

## File-level changes
**New:**
- `components.json`, `lib/utils.ts` (shadcn's `cn()` helper) — generated by `shadcn init`
- `components/ui/*.tsx` — generated by `shadcn add` (button, card, badge, avatar, tabs, textarea, select, alert, alert-dialog, skeleton, separator)
- `components/pr-list/PrList.tsx` — list shell, filter state, realtime subscription (moved from the old file, logic untouched)
- `components/pr-list/PrCard.tsx` — one PR's card shell (avatar, title, badge, date)
- `components/pr-list/FilterTabs.tsx` — filter row, now shadcn `Tabs`
- `components/pr-list/SummarizeAction.tsx`, `MergeAction.tsx`, `RequestChangesAction.tsx`, `CommentsAction.tsx` — the four action panels, moved + restyled, state machines untouched

**Modified:**
- `app/globals.css` — shadcn theme tokens + the font-circular-reference fix + removal of the stray `font-family: Arial` override
- `app/layout.tsx` — real `metadata` (title/description), font variable classNames moved to `<html>`
- `app/page.tsx` — import path update only (`components/PrList` → `components/pr-list/PrList`)
- `package.json` — new deps from `shadcn init`/`add`: `class-variance-authority`, `clsx`, `tailwind-merge`, Radix packages, `lucide-react`

**Deleted:**
- `components/PrList.tsx` (replaced by `components/pr-list/*`)

## Sequencing (each step is independently verifiable, sized for a session)

1. **shadcn/ui foundation** — `npx shadcn@latest init -d`, then immediately
   fix the font circular-reference gotcha and the `<body>`→`<html>` font
   variable move, then fix the stray `Arial` override and `layout.tsx`
   metadata. Verify: app builds, runs, Geist font now visibly renders
   (previously silently broken), no shadcn components used yet so layout is
   otherwise unchanged.
   - *New concept to explain first*: what `shadcn init` actually adds
     (`components.json`, the `cn()` utility, CSS-variable-based theming)
     before touching anything else.
2. **Split the file** — `components/PrList.tsx` → `components/pr-list/*`,
   zero visual/behavioral change. Verify: app looks and behaves pixel-
   identical to before the split.
3. **Card shell** — `Card`, `Avatar` (with the `next/image`-backed
   `AvatarImage`), `Badge` for status. Verify in browser.
   - *New concepts*: shadcn `Card` composition, `Badge` variants via `cva`,
     why `AvatarImage` needed customizing.
4. **Filter row** — hand-rolled pill buttons → shadcn `Tabs`, same `Filter`
   state. Verify filtering still works identically.
   - *New concept*: shadcn `Tabs` as a controlled component.
5. **Action toolbar** — stacked text links → `Button` group (icon + label,
   `variant="ghost"`, `size="sm"`), state machines untouched. Verify all
   four actions still trigger correctly.
   - *New concepts*: shadcn `Button` variants, lucide icon sizing (`h-4
     w-4`) convention.
6. **Action panel content** — `Alert` for error states, `AlertDialog` +
   `Select` for the merge confirm flow, `Textarea` for comment/
   request-changes input, `Skeleton` for the comments-loading state.
   Verify: summarize (incl. rate limit + cache), merge confirm/cancel,
   request-changes, comment post+list all still work end-to-end.
   - *New concepts*: `AlertDialog` vs `Dialog`, shadcn `Select`, `Skeleton`
     loading pattern.
7. **Accessibility pass** — `aria-live="polite"` on the realtime-updated
   list region, verify visible focus states on every interactive element,
   check badge color contrast (WCAG AA) if custom variants were added for
   open/merged/closed beyond shadcn's defaults.

`/code` executes these steps in order; each gets its own explanation-then-
build treatment per AGENTS.md's no-vibe-coding rule, and the running log
goes in `04-code-log.md`.

## Deferred to `/optimize` (data-driven, not speculative)
- Server/Client Component boundary restructuring (only if real Lighthouse
  numbers show it's needed).
- Any further bundle-size trimming, image-loading tuning, or caching
  strategy — decided from actual audit output, not guessed here.
